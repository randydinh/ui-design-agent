# Experience design

Use for shaping UX, user journeys, workflows, information architecture, or interaction behavior, including when no screen exists yet. The result should help the user decide how the product works before committing to a visual layout. Keep the method proportional: a focused improvement may need only a small task model and targeted flow; do not force a full journey, IA and study package into every request.

## Establish the working brief

Extract known user roles, goals, triggers, context, task frequency, existing workarounds, constraints, and the outcome that would count as success. Use supplied research, domain requirements, observations, and product evidence. Mark missing knowledge and ask only the question that would materially change the design; make reversible working assumptions when appropriate.

Separate:

- **Evidence:** cited observations, research, requirements, or verified product behavior.
- **Hypotheses:** inferred needs, pain points, expected behavior, and proposed success measures.
- **Design proposals:** flows, IA, content order, and interaction choices to evaluate.

Do not describe invented personas, synthetic interviews, or imagined usage scenes as validated research. A role description is a working model until supported. Do not invent backend functionality, telemetry availability, or regulatory requirements to make a journey complete.

## Map the experience

Describe the current journey when evidence exists and the desired journey from the trigger through completion and follow-up. For each meaningful step, capture user intent/action, system response, information needed, unresolved questions, and friction. If there is no current experience, label the starting model as a proposal.

Model workflows at the appropriate level: entry points, main path, decision points, alternate paths, cancellation, recovery, and terminal outcomes. Include relevant empty/loading/error states, permissions, capability limits, stale or unavailable data, interrupted work, and confirmation of consequential actions. Show state transitions and who can perform actions rather than listing screens alone.

Use concise journey tables, flow diagrams, or interaction examples when these make choices easier to assess. A diagram should express behavior, not decorative page boxes. Keep the scope focused on the user task; do not manufacture every imaginable edge case.

## Choose information architecture and content

Identify the decisions users need to make, then prioritize the information that enables them. Specify primary actions, supporting detail, grouping, labels, navigation, search/filter needs, and cross-surface continuity. Distinguish required information from optional improvements and data that needs engineering investigation.

Tie the interface hierarchy to the journey: what needs to be visible before an action, what belongs at the point of decision, and what can appear on demand. Keep the established domain vocabulary and propose clearer labels when evidence shows confusion. Reuse existing components and tokens after the behavior is understood.

## Compare viable options

When a meaningful design choice remains, present a small number of viable approaches with task-based tradeoffs, prerequisites, and a recommendation. For example, a persistent operations console may improve monitoring while a guided troubleshooting flow reduces novice decision load. Explain which audience/context favors each; do not ask users to choose between arbitrary color variants as a substitute for UX decisions.

The three lenses contribute to the same experience: Interface Design checks hierarchy and expression; UI UX Pro Max checks usability and states; Impeccable checks coherence, cognitive load, and clarity. For discovery, each specialist should contribute proposed behavior and options as well as identify risks. The lead reconciles them into one coherent flow.

## Plan validation

For consequential hypotheses, propose a testable validation plan: target participants or real user roles, representative tasks, prototype/evidence needed, observations or success measures, and a decision criterion. Prefer task completion, errors, comprehension, recovery, or time to identify the correct action over subjective attractiveness alone. Label targets as proposed until agreed.

Do not claim a usability study occurred because a specialist reviewed a design. If implementation is requested, identify which hypotheses can be checked in the delivered prototype and which still need user research or backend verification. Return the journey, proposed flow/IA, state requirements, options/tradeoffs, and validation plan through the report contract.
